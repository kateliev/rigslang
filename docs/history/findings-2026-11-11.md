# Findings: reason, intent, gate as one method

Date: 2026-11-11. Status: research notes from a brainstorming session. Web sources were read through search summaries; check the papers before you quote exact numbers.

## 1. The question

Can a reason–intent–gate method, with one elementary syntax, serve three scopes?

- build agents,
- build tools (apps in any language),
- build snippets of code for tools and agents.

Can the same notation also document code and logic, and act as persistent storage: pseudo-code that the agent writes for the human, in a clear form?

## 2. Short answer

Yes, with one condition: **the prose must be bound to something that runs.** A gate catalogue is useful because a checker refuses a gate without code and a rule that nothing reads. Without that binding, the method is model-driven development again, and that approach failed for known reasons (Section 6).

The two first memos are the same idea at two scales:

| Agent scale ([sidenote](sidenote-agent-configuration.md)) | Snippet scale ([self-writing language](self-writing-language.md)) |
|---|---|
| gate with a code verdict | `def` with a frozen body |
| gate decided by model judgment | hole: the answer is guessed |
| trigger / action / rules | intent / example / ensure |
| rule evidence | (missing: this was the gap) |
| verdict code | real runtime proof |

"Gate coverage" (the share decided by code) and "frozen against guessed" are the same measure. That is the spine of one method for all scales.

## 3. The minimal vocabulary

- **reason**: why it exists, with an `evidence` link. Documentation loses this first. Without it, the next agent cannot know whether a rule may change. *(Changed later: see Section 9.)*
- **intent**: what, in controlled language (ASD-STE100 style).
- **gate**: one of three kinds.
  - `hard`: code decides, and a fail blocks.
  - `soft`: code decides, and a fail is reported (compare DSPy `Assert` against `Suggest`).
  - `judge`: the model decides; the result is labelled as a guess.
- **example / ensure / cast**: the snippet layer.

The scope (agent, tool, snippet) changes how much you write, not the syntax. The full definition is in [../../skills/rig/spec.md](../../skills/rig/spec.md).

## 4. Documentation and persistent storage

The file *is* the documentation. The table view and the graph view are renderings of it.

It stays true only if drift is caught **in both directions** (a two-way hash):

- The intent changes → the cast remelts into a hole.
- The code changes and the intent does not → the intent is **stale**. The agent describes the code again; a human approves.

Persistent memory can use the same nodes: `fact` + `reason` + `evidence` + a last-verified date. Curation decides whether a self-written library grows or rots (see Ratchet in the [memo](self-writing-language.md)). Stored nodes need a rule that retires them, not only one that adds them.

## 5. Easier or harder?

| | Harder | Easier |
|---|---|---|
| Writing | Reason, intent and gate come before the code | The agent writes; the human cost moves from writing to reading |
| Review | | Read intent + verdict, not thousands of lines |
| Handoff | | Every model and every session reads the same catalogue |
| Drift | Two representations to keep in step | Drift is detectable (hash, checker) |
| Open-ended work | Forces structure that is not there | — |

**The largest risk is ceremony.** A review of spec-driven tools reports one small bug fix that became 4 user stories with 16 acceptance criteria, and finds review overhead and a false sense of control. The method must scale down to one line of intent and one `ensure`.

## 6. Who works in this direction, and what to learn

- **AgentSpec** (ICSE 2026): a DSL of trigger + predicate + enforcement for LLM agents, at runtime. LLM-written rules reached about 96% precision but about 71% recall. *Learn:* agents can draft gates; humans must look for the missing ones. Enforce gates in the runtime, not in the prompt: a gate that lives only in the context is a suggestion.
- **FlowBench** (EMNLP 2024): workflow knowledge as text, as code and as a flowchart. The flowchart was the best single format; all three together scored best. *Learn:* this supports "graph for flow, prose for judgment, code for verdicts".
- **Prompting with pseudo-code** (EMNLP 2023): pseudo-code instructions gave 7–16 F1 points over prose, on older small models.
- **Prompt formatting study** (2024): up to about 40% variance by format on smaller models; GPT-4 was much more robust. *Learn:* structure probably helps local and small models more than frontier models. Measure it.
- **DSPy**: signatures (what) separate from prompts (how), compiled. Assertions are hard and soft. *Learn:* the hard/soft gate split.
- **SudoLang**: pseudocode for LLMs, built on constraints and interfaces. Its author says it is for complex cases; for simple prompts, plain language is better.
- **PDL** (IBM, YAML) and **BAML**: prompts as typed functions with control flow. IBM reports up to 4× on a compliance agent.
- **Open Agent Spec** (Oracle, "ONNX for agents"): a framework-neutral graph format. *Learn:* for a universal version, be compatible with it rather than invent another serialization. It has no reason/evidence and no provenance (guessed against proved).
- **Statecharts** (XState / Stately Agent) and **LangGraph**: a deterministic machine outside, the model inside the nodes. No independent reliability benchmarks found.
- **Agent Skills / SKILL.md**: progressive disclosure. *Learn:* compile in layers: gate ids and names always loaded, briefs on demand.
- **Natural Language Outlines** (Google, FSE 2025): prose outlines aligned with code sections, kept in sync in both directions by an LLM. Models write good outlines only after examples of good outlines.
- **Spec-driven development** (Kiro, Spec Kit, Tessl): three levels — spec-first, spec-anchored, spec-as-source. *Learn:* stay **spec-anchored** (the spec stays alive and is checked). Use spec-as-source only at snippet scale, where a strong verifier exists.
- **BDD / Gherkin for agents**: scenarios as the contract for "done". Risk: with a vague requirement the model verifies its own interpretation.

## 7. What seems new

No system found combines all of these:

- reason and evidence as first-class nodes,
- provenance per node (hard / soft / judge) with a coverage number,
- cast and remelt with a two-way hash,
- one tiny grammar from agent down to snippet,
- human renderings (table and graph).

## 8. Cheap experiments, in order

1. **Format A/B** on a real agent: prose-only context against gate-compiled context against both. One local model and one frontier model. Count gate violations.
2. **Reverse documentation**: an agent writes Rig for one existing script. Time the human review. Regenerate code from the Rig file and run the tests: does the round trip hold?
3. **Snippet scale**: one geometry helper as a hole, cast by the skill. Geometry has clean `ensure` checks.

## 9. Naming

- **Rig**: Reason, Intent, Gate. A rig holds parts in place while work happens; rigging is lines under tension that guide the sails.
- *Changed after these findings:* **reason** now means the model's reasoning (the code it writes and the `judge` gates it decides), not *why* code exists. The `reason` node was removed: the intent is enough, and a `note` with `evidence` holds the rare remark that must stay with the code. See [logic.md](../logic.md).
- The working words come from hot-metal typefounding:
  - **matrix**: the spec of a unit; the mould from which every cast comes.
  - **cast**: verified code; the same matrix gives the same cast.
  - **proof**: the verification run (a test print, and a proof).
  - **remelt**: back to a hole. Linotype slugs were melted after printing and the metal was used again.
- Not yet checked for name collisions or trademarks.
